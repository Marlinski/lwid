lwid · protocol notes

AES-GCM with an openssl that refuses AES-GCM

This page was encrypted and published by a bash script using nothing but curl and openssl — no lwid binary. Getting there meant rebuilding GCM out of parts.

01The obstacle

lwid encrypts everything client-side with AES-256-GCM. So a push needs AES-256-GCM. And openssl enc — the obvious tool — simply will not do it: 

$ openssl enc -aes-256-gcm -K "$key" -iv "$iv" -in file
enc: AEAD ciphers not supported
enc: Use -help for summary.

This is deliberate, not a gap. enc streams data and has nowhere sensible to put an authentication tag, nor any way to tell you the tag failed to verify — so it declines the whole category. Nothing in openssl enc will produce a GCM tag.

The tag is not optional. Skip it and the browser's crypto.subtle.decrypt rejects the blob outright: in AEAD, a wrong tag is indistinguishable from tampering.

02The half that's easy

GCM's encryption is not a mode of its own — it is plain CTR. The only subtlety is where the counter starts. GCM reserves counter block J₀ = IV‖00000001 for the tag, so the plaintext begins one block later: 

openssl enc -aes-256-ctr -K "$key" -iv "${iv}00000002" -in plain -out ct

That is the ciphertext, byte for byte, done. What remains is the authenticator.

03The way in: GMAC

OpenSSL does expose GCM's authenticator — just not through enc. It lives in the mac command, as GMAC.

GMAC is GCM, with every byte fed as additional authenticated data instead of as plaintext. Both compute the same shape:

tag = ( GHASH(data blocks) ⊕ L ) × H ⊕ E(K, IV‖00000001)

Same key, same IV, and — if I hand GMAC the ciphertext — the same data blocks, so the same GHASH. The two differ in exactly one place: L, the trailing block that encodes how much of the input was AAD and how much was ciphertext.

GCM L = u64(0) ‖ u64(bitlen)
GMAC L = u64(bitlen) ‖ u64(0)
XOR bitlen ‖ bitlen

And because multiplication in GF(2¹²⁸) distributes over XOR, that single difference propagates cleanly through the multiply. The entire discrepancy between the tag OpenSSL will give me and the tag I need is:

tagGCM = tagGMAC ⊕ ( (bitlen ‖ bitlen) × H )

One multiply. Not one per block — one, whatever the file's size. OpenSSL still does every AES block and every GHASH block in C; the shell contributes a single 128-bit carry-less multiply at the end to correct the length block.

The subkey H is the one other thing needed, and it is just the block cipher applied to zero: 

H=$(head -c 16 /dev/zero | openssl enc -aes-256-ecb -K "$key" -nopad | bin2hex)
The multiply runs in pure shell arithmetic — two 64-bit halves, because that is the widest integer a shell has. It is the only piece of cryptography here not performed by OpenSSL, and therefore the only piece worth reviewing with suspicion.

04Everything else

With GCM solved, the rest of the protocol is ordinary primitives:

PieceHow
Ciphertextopenssl enc -aes-256-ctr, counter at IV‖00000002
GHASH subkeyopenssl enc -aes-256-ecb -nopad on a zero block
Authenticatoropenssl mac -cipher aes-256-gcm GMAC
Length fixupone GF(2¹²⁸) multiply, in bash
Content IDopenssl dgst -sha256, then base32
Write keyopenssl genpkey -algorithm ED25519
Signatureopenssl pkeyutl -sign -rawin over the root CID
Store tokensha256("lwid-store-auth:" + readkey)
Transportcurl

Two details that made this easier than expected

The manifest is plaintext JSON. Only paths and contents are encrypted. The server needs file sizes and blob CIDs to enforce quotas and garbage-collect, and those leak nothing once the rest is ciphertext — so there is no encrypted index to construct.

The signature covers just the CID string. No nonce, no timestamp, no canonical JSON — an Ed25519 signature over the root CID's ASCII bytes. Nothing to get subtly wrong.

Extracting raw key material is a small trick of its own: lwid stores an Ed25519 key as its bare 32-byte seed, and a PKCS#8 private key is a fixed 16-byte header followed by exactly that seed — so the raw material is the tail of the DER encoding. 

openssl pkey -in write.pem -outform DER         | tail -c 32   # seed
openssl pkey -in write.pem -pubout -outform DER | tail -c 32   # public key

05Whether it actually works

A cryptographic construction that is almost right produces output indistinguishable from one that is right, until someone tries to decrypt it. So the claim is not "this looks correct":

  • Byte-identical to a known-good GCM. Compared against Node's native aes-256-gcm at eight sizes, including empty and exact block boundaries.
  • The real client reads it back. Pushed with the script, then lwid cloned — byte-identical at 0, 1, 15, 16, 17, 100 and 5000 bytes. The Rust client verifies the tag, so a successful round-trip is proof the tag is right, not merely that the ciphertext is.
  • The CID is checked on every upload. The script derives each blob's address locally and compares it to the server's, so a hashing divergence fails loudly instead of yielding a manifest that points at nothing.
  • This page. You are reading it, which means Web Crypto accepted the tag — and it refuses a bad one.
